GAS長期運用ルール v2

GAS（スプレッドシートの自動化）を作ってもらうときに、後で困らないために守るルールです。

v1（17項目）を統合し、環境前提 + 8ルールにスリム化しました。

作成 2026-06-24 v2 改訂 2026-06-26 環境前提 + 8ルール
ゴールは 「書いた本人がいなくなっても、壊れない・止まらない・後から直せる」 GASを作ること。
このルールは、私や他のオンライン秘書（Claude）がGASを作る・チェックするときに自動で使われます。
v1 からの変更点
- 似ているルールを統合：A-1〜A-9 + B-1〜B-8（17項目）→ R-1〜R-8（8項目）
- 「環境前提」を独立セクション化（GitHub+clasp等が整っている前提を明示）
- AI（Claude）が読んでそのまま設計に使える指示書として最適化

環境前提

このルールは以下の環境が整っていることを前提にしています。未整備なら先に整備してください。

ENVGAS開発の前提環境

バージョン管理GitHub + clasp で管理する。「誰が・何を・なぜ変更したか」はGitのコミット履歴で残す。
GASデプロイ時のバージョンだけでは「誰が・なぜ」が分からず不十分。
デプロイフローclasp push でコードを反映する。push前に必ず前の状態をGitにコミット済みにする。
本番/テスト分離本番スクリプトとテスト用スクリプトを分け、テストで動作確認してから本番に反映する。
共有アカウントトリガー設定用の共有アカウントがある。個人アカウントでトリガーを設定しない。
タイムゾーンappsscript.json の timeZone は "Asia/Tokyo"。スプシ側も日本時間に揃える。
なぜ環境前提を分けたか？
ルール（R-1〜R-8）はコードの書き方。環境前提はコードの外側の話。
環境が整っていない状態でルールだけ守っても、履歴管理やトリガー管理が成り立たない。

設計ルール（8項目）

v1の17項目を統合。各項目に「何が困るか」+「どうするか」をセットで記載。

R-1シート参照：タブはGID、列はヘッダー名

🤔
なぜ困るタブ名はよく変わるし、列も挿入される。名前や番号で指定していると、ちょっとした変更で全部壊れる。
✅
やることタブは「ID（GID）」で指定。列は1行目の「見出し名」で認識する。どちらも変更に強い。
旧ルール：A-2（タブはIDで掴む）+ A-3（列は見出し名で）

R-2設定を集約して引き継ぎやすく

🤔
なぜ困る設定値がコードのあちこちに散らばっていると、直したい場所が見つからない。引き継ぎもできない。
✅
やること設定値（GID・通知先・チャンクサイズなど）を先頭の CONFIG 定数に集約。マジックナンバーを散らさない。命名規則も統一する。
旧ルール：A-6（引き継ぎやすい作り）

R-3パフォーマンス：まとめて読み書き + 6分制限対策

🤔
なぜ困る1マスずつ読み書きすると激遅（最大20倍差）。データが増えると「6分制限」で途中で止まる。
✅
やることgetValues() で一括取得 → 配列で加工 → setValues() で一括書き込み。件数が増える処理はバッチ分割し、続きから再開できる設計にする。
旧ルール：B-5（速く・軽く）+ B-1（6分制限で止まらない）

R-4エラーハンドリング：バリデーション + 通知 + リトライ

🤔
なぜ困る壊れやすい作りだと運用中に止まる。GAS標準の失敗通知は1日1回で、気づいたときには手遅れ。
✅
やること入口でおかしいデータを弾く。要所は try-catch で囲み、失敗したらSlackかメールに即通知。一時的な失敗は自動でやり直す。空catchで握りつぶさない。
旧ルール：A-5（エラーが起きにくく）+ B-4（失敗にすぐ気づく）

R-5排他制御 + トリガー管理

🤔
なぜ困る同時実行でデータがぶつかる。個人アカウントでトリガー設定すると退職時に止まる。古いトリガーを消し忘れると二重実行。
✅
やること同時実行は「順番待ち（ロック）」で防ぐ。トリガーは共有アカウントで設定し、作る前に古いのを消して1本だけにする。設定者と止め方を明記。
旧ルール：B-3（同時操作の事故防止）+ A-8（トリガー設定者）+ B-2（二重トリガー防止）

R-6機密管理：鍵やパスワードをコードに書かない

🤔
なぜ困るAPIキーやパスワードを直書きすると、共有した瞬間に流出する。
✅
やること鍵やパスワードはコードに書かず、安全な場所（スクリプトプロパティ）に入れる。必要なプロパティ名を仕様コメントに書いておく。
旧ルール：B-6（鍵を直書きしない）

R-7タイムゾーン：日本時間に統一する

🤔
なぜ困るGASの初期設定はアメリカ時間。放置すると日時が14時間ズレる（超あるある事故）。
✅
やることタイムゾーンを日本時間（Asia/Tokyo）に設定し、日付を文字に変換するときも必ずタイムゾーンを明示する。スプシ側とも揃える。
旧ルール：B-7（時間をズラさない）

R-8ドキュメント：仕様コメント + 関数タイトル + 不要コード削除

🤔
なぜ困る説明がないと引き継げない。古いコードが残っていると混乱する。関数が何をするか分からないと読み解けない。
✅
やることスクリプト先頭に「説明書（仕様コメント）」を置く。各関数に1行タイトル。使っていないコードは消す。
旧ルール：A-9（冒頭に説明書）+ A-7（関数にタイトル）+ A-4（不要コード掃除）

仕上げ(1) 冒頭に書く「説明書」のひな形

スクリプトの先頭にこの形を置いてもらう。引き継ぎ時にこれだけで運用が分かる状態に。
/**
 * ============================================================
 *  スクリプト名 : （例）日次売上集計
 *  目的         : 何を自動化するか1〜2行
 *  自動実行     : 毎日 7:00（設定者: 共有アカウント xxx@）
 *  対象シート   : ファイル名 or URL（タブID: 1234567890）
 *  連携先       : Slack通知 / 別スプシ「請求管理」/ 外部API
 *  必要な鍵     : API_KEY, SLACK_WEBHOOK_URL（プロパティに設定）
 *  実行アカウント: 誰の権限で動くか
 *  管理者/連絡先 : 担当者名（Slack @xxx）← 壊れたときの連絡先
 *  作成/最終更新 : 2026-06-24 / 担当者名
 *  止め方       : 自動実行の一覧から該当を削除（要 共有アカウント権限）
 * ============================================================
 */
